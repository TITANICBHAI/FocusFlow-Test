## What the Code Inspection Settles

**The double-counting isn't theoretical — it's already shipping.**

`ForegroundTaskService` syncs UsageStats into `daily_allowance_used` every 60 seconds. `AppBlockerAccessibilityService` writes elapsed time from its own timer into the same field on session close. The "raise only" guard prevents the UsageStats value from overwriting a higher event-based value, but it doesn't prevent the inverse: AccessibilityService's full session elapsed time landing *on top of* a UsageStats value that already captured part of that same session.

The document's 5-minute → 7-minute example is the actual bug. This is the most urgent fix, not a future risk.

**The current recovery mechanism is weaker than the architectural docs assumed.**

Session-start persistence + gap charging on reconnect is not checkpointing. The architectural docs described it as a foundation to build on. It's actually closer to the problem itself — gap charging can overcharge if the user switched apps during the gap, and it fails entirely if the process is killed without reaching `onInterrupt()`. The 15–30s checkpoint proposal was correct but it's a net-new addition, not an incremental improvement.

**Count mode has a specific service-restart double-increment path.**

`currentTimedPkg` in memory prevents repeated increments during a session. A restart clears it. If the user stays in the same app across a restart, the next accessibility event looks like a new foreground entry. UsageEvents reconciliation on reconnect directly addresses this, which is now the most concrete justification for that recommendation.

## What's New That Wasn't in the Architectural Docs

**The timezone bug is a concrete daily correctness failure.**

Kotlin uses device local time for allowance dates. TypeScript uses `toISOString()` which is UTC. Near midnight, these can disagree on which day it is. A user's usage at 11:55pm local time could be attributed to different days by the enforcement engine vs. the UI. This is not a theoretical edge case — it fires for any user in a UTC+ timezone using the app near midnight.

Fix is straightforward: align both sides to the same timezone. Device local time is the correct choice since that's what the user experiences as "today."

## Updated Priority Order

Given what the code actually does:

1. **Fix the ForegroundTaskService / AccessibilityService writer conflict.** The cleanest approach: `ForegroundTaskService` skips writing to `daily_allowance_used` for any app where `AccessibilityService` currently has an open session. This requires a shared signal — a lightweight SharedPreferences key like `active_session_pkg` that AccessibilityService sets on session open and clears on close. ForegroundTaskService reads it before writing. If there's an active session for that app, it defers. This is safer than removing ForegroundTaskService entirely, which could regress historical reporting.

2. **Add real per-session checkpointing.** Replace gap charging with periodic elapsed-time snapshots. AccessibilityService owns the timer, writes the checkpoint. On reconnect, recover from the checkpoint rather than charging the full elapsed gap.

3. **Fix the timezone mismatch.** Align TypeScript date calculation to device local time. This is a small code change with concrete correctness impact.

4. **Fix the bridge silent failure.** Separate availability method, don't change `setDailyAllowanceConfig` signature.

5. **Add UsageEvents reconciliation for count on reconnect.** Specifically to handle the double-increment-on-restart case identified above.

6. **UsageStats reporting fixes separately.** Sub-minute apps, rounding — confirmed bugs but don't touch enforcement.

## One Specific Caution on the ForegroundTaskService Fix

Before removing or gating `ForegroundTaskService`'s writes, verify whether anything else consumes `daily_allowance_used` from *its* perspective — i.e., whether any screen or report reads it expecting both sources to have written. If something renders usage totals from `daily_allowance_used` directly, gating the ForegroundTaskService writes could make those totals look lower than expected. The fix is still correct, but the reporting layer needs to be checked before landing it.
