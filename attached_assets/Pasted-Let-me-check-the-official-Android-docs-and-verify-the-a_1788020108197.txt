**✅ What checks out against official docs**

**App Info deep link** — Kotlin uses `Settings.ACTION_APPLICATION_DETAILS_SETTINGS` with `Uri.parse("package:${reactContext.packageName}")`. This is the official AOSP intent — the data URI specifies the application package name with the "package" scheme, e.g. "package:com.my.app". [Microsoft Learn](https://learn.microsoft.com/en-us/dotnet/api/android.provider.settings.actionapplicationdetailssettings?view=net-android-35.0) Works on every Android version since API 9. No concerns.

**Accessibility settings deep link** — Kotlin uses `Settings.ACTION_ACCESSIBILITY_SETTINGS`. This is the official `"android.settings.ACCESSIBILITY_SETTINGS"` intent, added at API level 5, documented as an action to show settings for accessibility modules. [mit](https://stuff.mit.edu/afs/sipb/project/android/docs/reference/android/provider/Settings.html) Universal. JS-side fallback `Linking.sendIntent('android.settings.ACCESSIBILITY_SETTINGS')` is the identical string — confirmed. ✅

**Restricted settings detection** — Kotlin checks the `"android:access_restricted_settings"` AppOps string. This restriction is tied to the `ACCESS_RESTRICTED_SETTINGS` AppOp permission. When an app is newly installed via the non-session-based API, the mode is set to "deny" — causing the accessibility toggle to be greyed out. After the user taps the toggle, the mode becomes "ignore" but is still blocked. Only after App Info → ⋮ → "Allow restricted settings" does the mode become "allow". [Android 13](https://www.android13.xyz/2023/01/android-13-new-restricted-settings.html)

The Kotlin checks `mode != AppOpsManager.MODE_ALLOWED`, which correctly catches both the initial "deny" AND the post-dialog "ignore" state. Returns false on any exception (safe failure, no false positives). ✅

Change it to something like:
