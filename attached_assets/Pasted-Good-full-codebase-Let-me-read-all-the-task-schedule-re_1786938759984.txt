**The architecture has 12 synchronization problems. Let me rank them by how badly they hurt the user.**

---

**Critical — these break things silently**

**1. `updateTask` doesn't update SharedPrefs when the active task changes mid-session.**
`updateTask` writes to the DB and reschedules expo-notifications reminders, but if the task being updated is the currently active focus session, it never touches the SharedPrefs keys (`task_name`, `task_end_ms`) that `ForegroundTaskService`, `AppBlockerAccessibilityService`, and the block overlay all read. So editing a task title or end time while a session is running leaves those three Kotlin services running with stale data. Only `extendTaskTime` correctly calls `SharedPrefsModule.setActiveTask()` afterward — `updateTask` doesn't.

**2. `completeTask` never calls `compressSchedule`.**
`compressSchedule` exists in `schedulerEngine.ts` and is supposed to pull subsequent tasks forward when a task finishes early. It's never called anywhere. `extendTask` correctly calls `rebalanceAfterOverrun` to push tasks back, but the symmetrical pull-forward on early completion is dead code. The schedule silently accumulates gaps.

**3. NOTIF_ACTION can double-fire when the app is in the foreground.**
`TASK_NOTIFICATION_BG` in `backgroundTasks.ts` handles Complete/Extend from background notification taps — it goes directly to the DB. `AppContext` also subscribes to `NOTIF_ACTION` from `EventBridge` for the same actions. If the app is foregrounded when the user taps the notification action, both paths can execute: the background task writes to DB, and AppContext writes its own update on top of stale `stateRef` state. The result is a double DB write and state/DB desync.

---

**High — degrade reliability**

**4. `addTask` schedules expo-notification reminders but never schedules the TaskAlarmModule end alarm.**
`TaskAlarmModule.scheduleAlarm()` — the Doze-immune AlarmManager alarm that fires the full-screen alarm at task end — is only ever called from the focus screen when a session starts. Adding a task via `addTask` or `QuickAddModal` never schedules this alarm. Tasks with focus mode enabled won't get the reliable end alarm unless the user navigates to the focus tab and the session auto-starts.

**5. `backgroundTasks.ts` OVERRUN_CHECK shifts subsequent tasks but doesn't update their TaskAlarmModule alarms.**
When `rebalanceAfterOverrun` shifts a task forward by, say, 10 minutes, the overrun handler calls `scheduleTaskReminders` (expo-notifications) but does NOT call `TaskAlarmModule.cancelAlarm` + `scheduleAlarm` for the shifted tasks. Those tasks' AlarmManager-based end alarms will still fire at the original times — potentially mid-focus on the previous task.

**6. `focusService.ts` holds a stale `currentTask` module-level reference after `extendTaskTime`.**
`extendTaskTime` in AppContext updates SharedPrefs and the DB with the new end time, but `focusService.ts`'s module-level `currentTask` variable was set at session start and is never updated. `getCurrentFocusTask()` returns the old task object for the rest of the session. Anything that calls it after an extension gets the wrong end time.

**7. `deleteTask` leaves subsequent tasks' times untouched.**
Deleting a task creates a gap in the schedule with no auto-compress. This is perhaps intentional — you may not want auto-shifting on delete — but there's also no user-facing prompt to optionally pull tasks forward. The gap silently stays.

---

**Medium — edge cases that surface occasionally**

**8. Two independent 30-second timers are running simultaneously.**
AppContext has its own `setInterval` at 30s for widget sync and standalone block expiry. `ForegroundTaskService` also emits `TASK_TICK` every 30s. AppContext never subscribes to `TASK_TICK` — it fires into the void. So you have two async timers independently writing to SharedPrefs, with no coordination. They can collide during a focus session.

**9. `TASK_ENDED` from native is received and immediately ignored.**
The AppContext subscription logs a message and does nothing. The focus screen shows "Time's up" based on its own local state polling. If the focus screen isn't mounted when `TASK_ENDED` fires, the event is completely lost — no navigation, no state update, no record.

**10. RecurringBlockSchedule → GreyoutWindow sync only happens inside `updateSettings`.**
If the app crashes during a settings save, the GreyoutModule can hold stale window data from the previous run with no recovery path at startup. There's no sync-on-boot or sync-on-resume guard.

**11. BootReceiver clears `focus_active` for indefinite standalone blocks.**
BootReceiver checks `endTimeMs > now` to validate whether to restore a session. Standalone blocks with no expiry have `task_end_ms = 0`, which fails that check, so the block is silently cleared on reboot even though it should persist.

**12. `skipTask` doesn't call `rebalanceAfterOverrun` or offer to pull tasks forward.**
Skipping a task (especially mid-session) is semantically the same as an early finish — there's freed time. But `skipTask` just marks the task and cancels its reminders, leaving subsequent tasks at their original times.
