## 1. CONFIRMED FIXES

### 1.1 Boot rearm — fixed and improved
`BootReceiver.kt:57-78`

The fix goes beyond what was recommended. `persistentVpn` is now resolved before the session branch and two things happen unconditionally:

```kotlin
if (persistentVpn && netBlockEnabled && selfHeal) {
    VpnWatchdogReceiver.schedule(context)
}
if (persistentVpn && netBlockEnabled && isUserUnlocked(context)) {
    NetworkBlockerVpnService.requestRecoverySync(context)
}
```

The `isUserUnlocked()` guard (`BootReceiver.kt:116-120`) is a correct addition. On Android 7+ with file-based encryption, `BOOT_COMPLETED` fires before user data is decrypted. Without this check, `requestRecoverySync` would run against encrypted SharedPrefs and read all defaults. The `USER_UNLOCKED` broadcast fires the receiver a second time once the user authenticates, and then `isUserUnlocked` returns true. This is the right design.

---

### 1.2 Two-write-path collision — resolved
`NetworkBlockModule.kt:202-210`, `SharedPrefsModule.kt:421-432`

`setNetworkBlockSettings` now writes to `net_block_explicit_packages` and `net_block_standalone_vpn_packages` as separate coordinator inputs, not to `net_block_packages` directly. The coordinator owns the merge and is the single writer to `net_block_packages` via `requestSyncInternal`.

`setVpnSelectedPackages` in `SharedPrefsModule` still exists as a compatibility shim for pre-update installs but now writes to `net_block_explicit_packages` and calls `requestSync`. `AppContext` no longer calls it at all. No collisions remain on the normal path.

---

### 1.3 PackageInstallReceiver VPN gap — fixed
`PackageInstallReceiver.kt`

Three changes, all correct:
- Now handles `PACKAGE_REMOVED` and `PACKAGE_FULLY_REMOVED` so removed packages are evicted from the effective target set without waiting for the next session sync.
- Uses `editor.commit()` (synchronous) before `requestSync` so the coordinator reads the already-updated `PREF_SA_PKGS`, not the stale value.
- Calls `NetworkBlockerVpnService.requestSync(context)` which delegates to the coordinator, instead of rebuilding a raw intent manually.

---

### 1.4 Native policy coordinator — implemented
`VpnPolicyCoordinator.kt`

Core design is solid:
- Kotlin `object` singleton — no class instantiation overhead.
- `synchronized(syncLock)` serializes concurrent writers from JS bridge (ReactMethod thread), AccessibilityService (main thread), and BroadcastReceivers.
- 150ms debounce via `mainHandler.postDelayed` coalesces rapid source changes.
- `forceRecovery = true` skips the debounce for receiver-driven paths where `onReceive` must finish before Android reclaims the process.
- All package lists are `.sorted()` before persistence and comparison — fixes the ordering equality bug from v1.
- `sameServiceState` compares sorted lists, so `["a","b"]` and `["b","a"]` are correctly treated as equivalent.
- Versioned desired-policy record (`generation`, `updatedAt`, `reasons` per package) enables forensic debugging.
- `ALWAYS_EXCLUDED` is now defined once in `VpnPolicyCoordinator` and referenced by `NetworkBlockerVpnService` — no duplicate list.

---

### 1.5 400ms race — eliminated
`AppContext.tsx:1606-1627`

`stopFocusMode` no longer does a stop-then-delayed-restart. It calls `stopNetworkBlock`, which in `NetworkBlockModule.kt:375-382` detects a persistent VPN configuration and calls `requestSync` instead of issuing a hard stop. The coordinator recalculates the effective set — dropping focus-derived targets while keeping explicit always-on packages alive — and dispatches atomically. No delay, no race.

---

### 1.6 Generation-based stale command guard — implemented
`NetworkBlockerVpnService.kt:511-519`, `onStartCommand:167`

`isStalePolicyCommand` rejects any ACTION_STOP or ACTION_START whose generation is lower than the current persisted generation. This prevents a delayed recovery dispatch (e.g., from `onRevoke`'s 3-second retry) from overwriting a newer policy that arrived in the meantime.

---

### 1.7 `intentionalStopRequested` — correct
`NetworkBlockerVpnService.kt:142, 168, 304-318`

`onDestroy` now rearms the watchdog only when the destruction was not intentional:

```kotlin
val shouldRearmRecovery = !intentionalStopRequested &&
    prefs.getBoolean("net_block_enabled", false) && ...
```

`stopVpn()` cancels the watchdog because it is shared between intentional and unintentional teardown. This flag is the tiebreaker. Without it, an intentional stop would cancel the watchdog and then `onDestroy` would rearm it, defeating the cancellation.

---

### 1.8 Manifest and installer — both updated correctly
`install.sh:PackageInstallReceiver section`, `withFocusDayAndroid.js:360-407`

Both the installer and the Expo plugin handle the upgrade case: if `PackageInstallReceiver` already exists in the manifest but lacks `PACKAGE_REMOVED` or `PACKAGE_FULLY_REMOVED`, the actions are appended individually. Fresh installs get all three at once. `VpnPolicyCoordinator` is a Kotlin `object` — no manifest entry needed, no module registration required. The `services/*.kt` glob in `install.sh` copies it automatically.

## 2. REMAINING ISSUES

### 2.1 `queryIntentActivities` runs under `syncLock` on the main thread — ANR risk
`VpnPolicyCoordinator.kt:125-155, 287-304`

`requestSyncInternal` holds `syncLock` while calling `effectivePolicy()`. When `net_block_focus_mirror` is true and a focus session is active, `effectivePolicy` calls:

```kotlin
context.packageManager.queryIntentActivities(launcherIntent, 0)
```

This is a synchronous Binder IPC call to the package manager. On a device with 200+ installed apps it can take 15–50ms. Several callers arrive on the main thread:

- `PackageInstallReceiver.onReceive()` — main thread by definition.
- `AppBlockerAccessibilityService.checkAndHealVpn()` — invoked from `vpnHealthRunnable` which posts to `Looper.getMainLooper()`.

If `packageManager` is under load (other app installs, OEM overlay scanning), this can exceed the 5-second ANR threshold for BroadcastReceivers or delay AccessibilityService events.

**Fix:** Cache the launcher package list with a short TTL (30–60 seconds) in a `@Volatile` field, refreshed outside the lock on a background thread. Only call `queryIntentActivities` when the cache is stale.

```kotlin
@Volatile private var cachedLauncherPackages: List<String> = emptyList()
@Volatile private var cacheRefreshedAtMs: Long = 0L
private const val LAUNCHER_CACHE_TTL_MS = 30_000L
```

---

### 2.2 `startNetworkBlock` writes `net_block_packages` before the coordinator
`NetworkBlockModule.kt:287-290`

```kotlin
prefs.edit()
    .putString("net_block_packages", effectivePackagesJson)
    .putString("net_block_mode", ...)
    .apply()
```

This write happens before `VpnPolicyCoordinator.requestSync()` is called. The coordinator then overwrites `net_block_packages` in `requestSyncInternal`. The intermediate value serves no purpose and creates a brief window where `net_block_packages` holds a value that bypassed the coordinator's generation tracking and sorted deduplication. Remove those two lines — the coordinator handles the write.

---

### 2.3 `focusMirrorVpnEnabled` is not backed up or restored
`backupService.ts` — no reference to `focusMirrorVpnEnabled`

Every other VPN setting (`vpnBlockEnabled`, `vpnSelfHealEnabled`, `alwaysOnVpnPackages`, `standaloneVpnPackages`) is included in the backup. `focusMirrorVpnEnabled` is in `types.ts:178` and `defaultSettings.ts:43` but absent from `backupService.ts`. A user who migrates devices or reinstalls loses this setting silently and defaults to `false`, which is safe but surprising.

**Fix:** Add `focusMirrorVpnEnabled` to the backup serialisation and restore path in `backupService.ts`.

---

### 2.4 `isNetworkBlockActive` still returns process-local `isRunning`
`NetworkBlockModule.kt:403-405`

```kotlin
fun isNetworkBlockActive(promise: Promise) {
    promise.resolve(NetworkBlockerVpnService.isRunning)
}
```

`isRunning` is `@Volatile` and resets to `false` on process death. After a process kill with the tunnel still alive, this returns `false` while `vpn_status` SharedPref still reads `"running"`. `getNetworkBlockStatus` now exposes both fields (`running` and `state`), so the UI can reconcile them — but `isNetworkBlockActive` is still misleading on its own. Not a regression from v1 but worth noting if anything uses this call as a single source of truth.

### 2.5 Manual JSON quoting in `SharedPrefsModule` — still present
`SharedPrefsModule.kt:298-299` (`setAlwaysBlockActive`), `setAllowedPackages`, `setDailyAllowancePackages`

```kotlin
val list = (0 until packages.size()).map { "\"${packages.getString(it)}\"" }
val json = "[${list.joinToString(",")}]"
```

Pre-existing. Not introduced or fixed in this version. Android package names follow strict identifier rules so real-world risk is near-zero, but it's inconsistent with the coordinator's `JSONArray`-based serialisation.

## 5. BUILD CONCERNS

### 5.1 `QUERY_ALL_PACKAGES` and the focus mirror feature
The focus mirror feature (`VpnPolicyCoordinator.kt:287-304`) calls `queryIntentActivities` with an implicit `ACTION_MAIN / CATEGORY_LAUNCHER` intent. On Android 11 (API 30+), this returns only system apps and explicitly queried packages unless `QUERY_ALL_PACKAGES` is granted.

`install.sh` already patches this permission in. However:
- Google Play requires a declaration and justification in the Play Console for `QUERY_ALL_PACKAGES`. FocusFlow already uses this permission for its app-picker, so no new Play review burden is introduced by the VPN focus mirror feature specifically.
- If `QUERY_ALL_PACKAGES` is not granted (sideload builds, managed profiles, some OEM restrictions), `queryIntentActivities` returns a partial list. The focus mirror blocking will be incomplete — it will miss apps that aren't system apps or declared in `<queries>`. This is silent, not a crash, but the user's focus session loses some enforcement coverage.

### 5.2 `foregroundServiceType="specialUse"` on the VPN service
`install.sh` and the plugin both declare `NetworkBlockerVpnService` with `foregroundServiceType="specialUse"` and the required `PROPERTY_SPECIAL_USE_FGS_SUBTYPE`. This is correct for Android 14 (API 34). Builds targeting API 33 or below do not require this attribute but it is harmless there. No action needed unless your `targetSdkVersion` is below 34.
