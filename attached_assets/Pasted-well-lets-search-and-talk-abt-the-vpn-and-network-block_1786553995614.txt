I found a likely primary reason the VPN blocker does nothing:

Critical bug: the UI toggle never enables the native VPN flag
The UI updates:

vpnBlockEnabled

and syncs that to:

net_block_enabled

But the native VPN service separately checks:

net_block_vpn

Both NetworkBlockModule.startNetworkBlock() and the Accessibility Service require net_block_vpn == true.

The only native code that writes net_block_vpn is inside setNetworkBlockSettings(), but the JavaScript bridge does not expose or call that method. So on a normal install:

net_block_vpn = false

forever.

That means:

The user enables VPN blocking in the UI.
The UI says it is enabled.
net_block_enabled becomes true.
The Accessibility Service checks net_block_vpn.
It sees false and immediately returns.
No VPN tunnel is started.
This is more fundamental than Android auto-revoking the permission.

Other serious failure points
1. VPN startup can be silently rejected
Both normal startup and the Accessibility Service use:

startService(intent)

instead of a foreground-service start on newer Android versions. Android may reject that when the app is in the background. The exception is swallowed, so the user sees no failure.

2. Startup reports success even when VPN is skipped
If permission is missing, startNetworkBlock() simply skips the VPN and resolves successfully:

if (vpnPermission == null) {
   // start
}
// otherwise silently skip
promise.resolve(null)

So the JavaScript layer cannot distinguish:

VPN actually started
permission was revoked
another VPN owns the slot
Android rejected service startup
VPN was disabled in native preferences
3. Per-app package failures are hidden
This code suppresses every failure:

packages.forEach { pkg ->
    runCatching { builder.addAllowedApplication(pkg) }
}

If package registration fails, the tunnel may still be established and isRunning becomes true. The app then believes protection is active even though the selected package may bypass it.

4. The first package can determine the entire session
The Accessibility Service starts the VPN with only the currently blocked package:

val pkgs = JSONArray().apply { put(blockedPackage) }.toString()

Then it refuses to start another VPN while one is already running:

if (NetworkBlockerVpnService.isRunning) return

In per-app mode, that means the first blocked app can be routed through the VPN while later blocked apps are not added to the tunnel.

This only works reliably if the VPN is started up front with the complete package list.

5. Preference names are inconsistent
There are currently multiple package lists:

net_block_packages
vpn_selected_packages
alwaysOnVpnPackages
standaloneVpnPackages
The Accessibility Service uses vpn_selected_packages to decide whether it should trigger the VPN, while the VPN service restores from net_block_packages.

Those lists can disagree, producing cases where the UI says an app is selected but the native VPN receives a different list.

6. Permission re-grant exists, but only after the app returns
The app does detect revoked permission when its React UI is foregrounded. The banner checks:

VpnService.prepare()

again when the app becomes active.

However:

Android does not allow silently re-granting VPN consent.
The Accessibility Service cannot safely pop the consent dialog while another app is foregrounded.
The native self-heal path only retries if vpnSelfHealEnabled is true.
The one-shot retry catches and discards all failures.
If the banner has no package list, it hides after re-granting without necessarily restarting the VPN.
So the current behavior is not “never request again”; it is closer to “request again only when the React app is open and the banner is mounted.”

7. Default values contradict each other
The Kotlin documentation says VPN is enabled by default:

net_block_vpn // recommended, default true

But getNetworkBlockSettings() reads:

prefs.getBoolean("net_block_vpn", false)

The JavaScript settings defaults also use false.

This makes the behavior confusing and can leave the UI/native state out of sync.

8. The native module registration must be verified in the built APK
The source contains FocusDayPackage, but the manifest documentation still says MainApplication.kt needs a manual registration step. If the generated Android project does not include:

packages.add(FocusDayPackage())

then all JavaScript calls become no-ops. The JS wrapper even intentionally hides that failure:

if (!NetworkBlock) return;

This should be checked in the actual generated Android build.

My recommended repair order
Synchronize the UI toggle to both native flags, or remove the duplicate net_block_vpn flag.
Start the VPN with the proper foreground-service API on Android 8+.
Return explicit failure states instead of resolving successfully when permission/startup fails.
Stop swallowing package-registration errors and expose the actual VPN health state.
Use one canonical package list and rebuild the per-app VPN when the list changes.
Keep the foreground re-grant banner, but make it show clear states such as:
permission missing
another VPN active
VPN service failed to start
tunnel running but package list not installed
Verify FocusDayPackage registration in the generated APK.
I have not changed the code yet; this was an investigation pass. The net_block_vpn synchronization issue is the first thing I would fix because it can explain the entire blocker appearing enabled while never starting.
