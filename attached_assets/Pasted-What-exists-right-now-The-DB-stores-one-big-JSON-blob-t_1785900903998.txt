What exists right now

The DB stores one big JSON blob — the entire AppSettings object as a single key=app_settings row. Read once on cold start, dispatched to React context, then JS pushes relevant fields to SharedPrefs via the _sync* functions.

SharedPrefs is currently a downstream copy — written by JS after every save and every cold start. The Kotlin services (AccessibilityService, BootReceiver, ForegroundService) read exclusively from SharedPrefs and never touch the DB.

The gap: if the DB is slow or deleted, JS pushes defaults (empty) to SharedPrefs, wiping the real enforcement config.

Proposed architecture

Group A fields become SharedPrefs-primary. DB becomes a backup copy for those fields only. Flow changes to:
User saves a Group A setting
  → write to SharedPrefs (immediate, atomic, can't be timed out)
  → write to DB (backup, for export/restore)
Cold start
  → read Group A fields from SharedPrefs IMMEDIATELY (fast, no timeout risk)
  → read full AppSettings from DB (8s timeout, for the JS layer)
  → if DB succeeds: merge DB values over SP values (DB wins for export accuracy)
  → if DB times out: SP values are already live in context — nothing gets wiped
Backup/export
  → reads from DB blob as now (Group A fields in DB blob stay in sync because every save writes both)

Group B stays push-on-save as it is. Those modules have their own internal state and don't boot before JS.

Group C stays DB-only.
Implementation steps (in order)

Step 1 — SharedPrefs read on startup (Kotlin side) Add a readEnforcementSettingsFromSP() helper in the TS wrapper that reads all Group A fields from SharedPrefs and returns them as a partial AppSettings. Called at the start of init() before the DB read. These values populate context immediately and are used for the native sync, with no timeout risk.

Step 2 — Merge on DB load After dbGetSettings() resolves, merge the DB result over the SP snapshot. DB wins (it's the more precise/validated copy). Dispatch the merged result to context. The native sync runs with the DB-accurate values.

Step 3 — Dual-write on every Group A save All existing save paths (setDailyAllowanceEntries, setStandaloneBlockAndAllowance, setStandaloneBlock, updateSettings for the boolean flags) already write to both DB and SP. Audit each one to confirm the SP write happens before the DB write (so even if DB fails, SP is up to date). Fix any that have the order wrong.

Step 4 — SharedPrefsModule.kt — add a bulk-read method Add getAllEnforcementSettings() on the Kotlin side that returns all Group A keys as a single JSON object. This avoids 17 separate async calls on startup and keeps the startup path fast.

Step 5 — Remove the dbLoaded gate from Fix A Once Step 1+2 are in place, the if (dbLoaded) gate I added is no longer the main defence — the SP-first read is. We can simplify the startup back to always running the native sync (it will use real SP-sourced data, not empty defaults).
What this does NOT change

    The DB schema — still one JSON blob for app_settings
    The Task/FocusSession/stats tables — untouched
    Backup/export format — DB blob still has all settings, Group A fields stay in sync
    The Kotlin services — they still only read from SharedPrefs, same as now

Want to go ahead with this plan? I'd do Steps 1–4 in one pass since they're all connected, then Step 5 as a cleanup.
