**There are three separate problems, not one. They happen in sequence and reinforce each other.**

**Problem 1: The stuck screen (the trigger)**

`active.tsx` runs a `setInterval` every 5 seconds inside `useFocusEffect` that hits `dbGetRecentDayCompletions`, `dbGetTodayFocusMinutes`, and `dbGetTodayOverrideCount`. Each of those calls goes through the database layer which has timeouts of 3–8 seconds when the DB handle is dying (you can see "3087ms", "15291ms" in the log).

When the DB starts failing, these calls don't fail fast — they hang until the timeout fires. A new interval tick arrives every 5 seconds. You now have overlapping DB calls all hanging simultaneously, all competing on the JS thread. The UI freezes because the JS event queue is backed up with pending promise chains that each take 3-15 seconds to resolve. The `mounted` flag prevents state updates after unmount but does nothing to stop the calls from being made. The screen looks stuck because it is — the JS thread is consumed.

**Fix is one line** — add a `state.isDbReady` guard at the top of the refresh callback so when the DB is dead it bails immediately instead of firing a chain of hanging calls:

```typescript
const refresh = (force = false) => {
  void refreshLiveData(force);
  void (async () => {
    if (!state.isDbReady) return; // ← add this
    try { ...DB calls... }
  })();
};
```

But `isDbReady` stays true even on the recovery DB, so you also need to track `isDbUnrecoverable` in AppContext state and expose it. When the recovery DB also fails (`DB_UNRECOVERABLE`), set that flag, and the interval bails entirely.

**Problem 2: The VPN errors (a consequence of DB recovery)**

The log shows this at `07:11:50`, right after `DB_CORRUPTION_RECOVERY`:

```
vpn settings sync failed: Error: A Defense Password is required
VPN stop after disabling failed: Error: A session PIN or Defense Password is required
```

What's happening: the recovery DB has no data, so `dbGetSettings()` returns `DEFAULT_SETTINGS` which has `vpnBlockEnabled: false`. `_syncGuardRails` then calls `setNetworkBlockSettings({ enabled: false, ... })` and `stopNetworkBlock(null)` — both with `defensePinHash: null`. The native side correctly rejects because a session with a PIN is active.

This is not a crash but it leaves JS state and native state diverged. JS thinks VPN is off. Native VPN is still running. The active screen then shows "Configured but stopped" or similar even though blocking is working.

**Fix**: In `_syncGuardRails`, before trying to disable VPN, check if we're operating on a recovery/empty DB. The signal is already available — if `settings === DEFAULT_SETTINGS` or if you add an `isRecoveryDb` flag, skip the VPN disable sync entirely during recovery. You never want to tear down live enforcement because the DB failed.

**Problem 3: The brown screen (a consequence of the wrong restart method)**

`ErrorFallback.tsx` calls `reloadAppAsync()` from `expo`. This only reloads the JavaScript bundle — it does NOT restart the Android process. The JSI NullPointerException that killed the DB handle is in the native layer. After JS reloads, the new JS context tries to open the DB, hits the same dead JSI bridge, NPEs again, hits `DB_UNRECOVERABLE` again, and the whole cycle repeats.

The "brown screen" is what the root view shows between the JS reload completing and the new init sequence finishing — essentially a blank canvas while React Navigation hasn't mounted yet. On a dark theme this reads as very dark brown/black.

**Fix**: Replace `reloadAppAsync()` with `BackHandler.exitApp()` in the error fallback. A full process kill forces Android to restart from scratch, which clears the dead JSI state. The user sees the normal cold-start splash, the DB opens cleanly, and everything works. The "Try Again" button should be a real exit, not a JS reload.

**To summarise — three files, each with one change:**

`active.tsx` — guard the refresh interval against an unavailable DB so it doesn't back up the JS thread.

`AppContext.tsx` — skip VPN disable sync when operating on a recovery/default-settings DB. Never attempt to tear down active enforcement because the DB failed.

`ErrorFallback.tsx` — replace `reloadAppAsync()` with `BackHandler.exitApp()` so the "Try Again" button actually clears the dead native state.

The DB NullPointerException on API 30 is the trigger for all three, but that's an Expo SQLite issue you can't fix directly — your job is to make the app survive it without cascading into a stuck screen, a VPN state divergence, and an unrecoverable crash loop.
