This architectural distinction clarifies the core friction in the app's current design:

* **`UsageStatsManager` / Usage Access Permission** is an asynchronous **reporting API**. It excels at providing aggregated historical metrics (foreground minutes, app-launch counts derived from `UsageEvents`), but Android intentionally buffers and flushes these events asynchronously. It is not designed to trigger real-time blocking standard to hard limits.
* **`AppBlockerAccessibilityService`** is a synchronous **enforcement engine**. It receives real-time UI/window events (`TYPE_WINDOW_STATE_CHANGED`), allowing it to intercept app launches immediately and draw overlay/block screens the millisecond a limit is exceeded.

---

### The Recommended Architecture: Hybrid Enforcement & Event Sourcing

To fix daily allowance failures, prevent counter drift, and remove redundant state management, refactor the two systems into complementary roles:

```
┌────────────────────────────────────────────────────────┐
│                   App Configuration                    │
│             (SQLite ──> SharedPrefs Sync)              │
│       [Limit Mode, Daily Budget, Interval Window]      │
└──────────────────────────┬─────────────────────────────┘
                           │
             ┌─────────────┴─────────────┐
             ▼                           ▼
┌──────────────────────────┐   ┌──────────────────────────┐
│  Accessibility Service   │   │    UsageStats Module     │
│   (Immediate Enforcement)│   │   (Historical Reporting) │
├──────────────────────────┤   ├──────────────────────────┤
│ • Window transition events│   │ • Total foreground time  │
│ • Active session timer   │   │ • Event-derived launches │
│ • Session checkpointing  │   │ • Analytics & Insights   │
└──────────────────────────┘   └──────────────────────────┘

```

#### 1. Shift to Android `UsageEvents` as the Source of Truth for Daily Open Counts

Instead of manually incrementing and storing a standalone `daily_allowance_used` launch counter inside `SharedPreferences` (which drifts if the accessibility service misses an event or gets restarted):

* On app launch or window state change, query `UsageEvents` for the current calendar day ($00:00 \text{ to NOW}$) to compute the day's true launch count on demand.
* This eliminates counter drift while maintaining instant real-time blocking capability.

#### 2. Implement Short-Interval "Checkpointing" for Active Time Budgets

Since `UsageStatsManager` lags in updating the *currently active app's* exact foreground duration until the user leaves the application:

* Use `AppBlockerAccessibilityService` to track **only the current active foreground session**.
* Save periodic active-session checkpoints (e.g., every 15–30 seconds) into a lightweight `SharedPreferences` cache key (`active_session_checkpoint`).
* **Calculation:** $\text{Total Usage Today} = \text{UsageStats Today} + \text{Active Session Checkpoint}$.
* If Android unexpectedly kills the `AccessibilityService` mid-session, the maximum lost duration is capped at the 15–30 second checkpoint window.

#### 3. Eliminate Silent Bridge Failures in `SharedPrefsModule.ts`

To ensure the UI never gives a false sense of security when running on builds where native modules are unlinked or missing:

```typescript
// src/native-modules/SharedPrefsModule.ts
export const setDailyAllowanceConfig = async (config: AllowanceConfig): Promise<boolean> => {
  if (!NativeModules.SharedPrefsModule?.setDailyAllowanceConfig) {
    if (__DEV__) {
      console.warn('[SharedPrefsModule] Native module unavailable. Native enforcement will not function.');
    }
    // Throw an explicit error or return false so AppContext knows sync failed
    return false; 
  }
  return NativeModules.SharedPrefsModule.setDailyAllowanceConfig(config);
};

```

### Summary of Component Roles

| Feature | Primary Source | Responsibility |
| --- | --- | --- |
| **Allowance Configuration** | SQLite $\rightarrow$ `SharedPreferences` | Stores limits, modes (Count/Time/Interval), and target package names. |
| **Live Enforcement** | `AccessibilityService` | Intercepts window state changes; enforces immediate blocks when counters expire. |
| **Active Session Tracking** | In-Memory + 15s Checkpoint | Tracks live foreground time of the active app without relying on stale `UsageStats`. |
| **Historical & Daily Insights** | `UsageStatsManager` / `UsageEvents` | Provides usage graphs, total daily time, and historical app launches for the UI. |

What permission is used for what
Usage Access permission
This is checked through:

AppOpsManager.OPSTR_GET_USAGE_STATS
UsageStatsManager.queryUsageStats(...)
UsageStatsManager.queryEvents(...)

Relevant file:

artifacts/focusflow/android-native/app/src/main/java/com/tbtechs/focusflow/modules/UsageStatsModule.kt

So if:

The user granted FocusFlow Usage Access
The installed build includes the custom native UsageStats module
Android returns usage history
then FocusFlow is getting usage time and foreground-entry counts from Android’s usage data.

The permission check is also reasonably defensive for Samsung and Huawei devices. It checks AppOps and sometimes verifies with a live usage query.

However, this does not guarantee fresh data. Android may delay updating the currently active app’s usage record.

Daily allowance uses a different mechanism
Daily allowance enforcement is handled by:

AppBlockerAccessibilityService.kt

It listens for live accessibility window changes:

onAccessibilityEvent(...)

That is how it immediately detects:

The user opened an app
The user switched away
The user is still inside the app
The allowance has expired
The accessibility service does not calculate the allowance from UsageStatsManager today. It uses:

daily_allowance_config
daily_allowance_used

in Android SharedPreferences.

That means there are currently two systems:

Purpose	Current source
Usage reports	Android UsageStatsManager / UsageEvents
Live allowance enforcement	Accessibility events
Allowance configuration	SQLite + SharedPreferences
Allowance counters	SharedPreferences
Why it may not be working even when Usage Access is correct
The most important point is:

Usage Access permission can be working correctly while daily allowance enforcement is still broken.

Daily allowance also needs the Accessibility Service to be enabled and running.

Additionally, the native allowance sync can silently do nothing if the custom native module is unavailable:

src/native-modules/SharedPrefsModule.ts:138-140

The code returns without throwing when setDailyAllowanceConfig is missing. Therefore:

The UI may show the allowance as saved
SQLite may contain the allowance
Usage Access may be granted
But the AccessibilityService may still have no allowance configuration
That is likely the first thing to verify on the actual Android build.

Can we just fetch everything from Usage Access?
For reports: mostly yes
For usage reports, it is better to trust Android’s Usage Access data than duplicate the same history in FocusFlow.

The app should continue using:

UsageStatsManager for total foreground time
UsageEvents for app-entry counts
There is no need to separately store every usage report row unless you specifically want historical snapshots or backup/export behavior.

For daily allowance configuration: no
The app still needs to store the user’s rules somewhere:

Which apps have limits
Count versus time mode
Daily budget
Interval duration
Interval window size
Android Usage Access does not know those user-defined limits.

For daily allowance usage counters: possibly
The current daily_allowance_used storage could potentially be reduced or removed as the primary source.

A better design would be:

Store the allowance configuration locally
Use Android UsageEvents to calculate today’s app-entry count
Use Android UsageStats for historical foreground time
Use the AccessibilityService for immediate real-time enforcement
Keep only a small current-session checkpoint so usage is not lost if the service dies mid-session
That would avoid maintaining a separate full usage counter that can drift from Android’s data.

Why Digital Wellbeing is not the right replacement
FocusFlow generally cannot directly read Digital Wellbeing’s private database or internal UI data.

Digital Wellbeing is a system app. For normal third-party apps, the supported public source is:

UsageStatsManager

Digital Wellbeing itself may have privileged access that FocusFlow does not have.

So the practical options are:

Usage Access API — supported, public, already used by FocusFlow
Accessibility Service — real-time foreground enforcement
Internal SharedPreferences state — current configuration/session checkpoint
Digital Wellbeing private data — not a reliable or supported integration
Direct answer
Is Usage Access permission being queried correctly?
Yes, for usage reports, assuming the custom native build is installed.

Is daily allowance currently using that permission?
No. It primarily uses Accessibility events plus its own native counters.

Can the app stop storing all usage separately?
Yes, likely for historical usage and most counters. The app should derive usage from Android where possible and only persist configuration plus an active-session checkpoint.

Can it fetch directly from Digital Wellbeing instead?
No—not reliably through a supported public API.

The cleanest fix is not to replace Usage Access with Digital Wellbeing. It is to make Android Usage Access the source of truth for reports, make Accessibility the source of truth for immediate enforcement, and remove or minimize duplicated allowance usage storage.
