## Verification Checklist

**The stale signal problem I flagged earlier — check this first**

The `active_session_pkg` key (or whatever you named it) that AccessibilityService sets to gate ForegroundTaskService writes needs a timestamp alongside it. If the service dies without clearing the key, ForegroundTaskService silently defers forever on that app. Confirm the implementation writes a timestamp with the signal and that ForegroundTaskService treats any signal older than a reasonable TTL (e.g., 2× the sync interval, so ~120s) as stale and proceeds normally.

**Checkpoint recovery path — verify it doesn't fall back to gap charging**

Confirm on reconnect the code reads the checkpoint value and resumes from it, not from `timed_session_open_at_ms` alone. The old gap-charging path should either be removed or only used as a last resort when no checkpoint exists at all. If both paths can run, you've added a new double-count source.

**The date fix — confirm it's device local, not just `new Date()` without explicit timezone**

`new Date().toISOString().slice(0, 10)` is UTC. The fix needs to explicitly format using the device's local timezone offset. Check that `formatLocalDate` (or whatever the helper is named) doesn't just call `toISOString()` internally — that's a common mistake.

**Count reconciliation tie-breaking**

On reconnect, when UsageEvents count disagrees with the stored count, confirm the code takes the **higher** value for enforcement. Taking the lower value could credit the user with opens that actually happened.

**ForegroundTaskService write gating — verify the skip is per-app, not global**

If App A has an active session, ForegroundTaskService should still update usage for Apps B, C, D. If the gating is applied globally (skipping the entire sync when any session is active), historical usage reporting will go stale during any active session.
