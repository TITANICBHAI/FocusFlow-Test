## Bugs Found

**CRITICAL — Alarms fire immediately for every past task on import**

`restoreFromJson` calls `cb.addTask(t)` for every task in the backup with no date or status filter. `addTask` always calls `scheduleTaskReminders`. `notificationService.ts` line 199 calls `TaskAlarmModule.scheduleAlarm(task.id, task.title, endMs)` with no guard:

```ts
// No check here — calls Kotlin unconditionally
void TaskAlarmModule.scheduleAlarm(task.id, task.title, endMs);
```

In `TaskAlarmModule.kt`, the Kotlin has an explicit branch:

```kotlin
if (triggerAt <= System.currentTimeMillis()) {
    // fires alarm notification immediately
    ForegroundTaskService.postTaskEndAlarmNotification(...)
    promise.resolve(true); return
}
```

The comment in `notificationService.ts` says *"only when in the future"* but that guard was never written. Importing a 50-task backup fires 50 immediate alarms. Importing completed and skipped tasks does the same — `addTask` doesn't check `task.status`.

**Fix:**

```ts
// notificationService.ts — add this guard before the scheduleAlarm call
if (Platform.OS === 'android' && endMs > Date.now()) {
    void TaskAlarmModule.scheduleAlarm(task.id, task.title, endMs);
}
```

And in `restoreFromJson` / `backupService.ts`, skip alarm scheduling entirely during import — let the existing `refreshTasks` call at the end re-arm whatever's needed:

```ts
// backupService.ts — change addTask callback signature to support no-alarm import
// Simplest path: add a skipAlarms flag in AppContext's addTask
await cb.addTask(t as Task, { skipAlarms: true });
```

**HIGH — Expo-notifications 500-notification limit**

Each task gets up to 8 scheduled notifications (-10m, -5m, -1m, start, 15m-in, 30m-in, T-1min, end). At 63 tasks you hit ~500. Android silently starts dropping the oldest ones. Import of a large backup makes this worse by scheduling all historical tasks at once.

The background fetch makes it worse again: `cancelTaskReminders` calls `getAllScheduledNotificationsAsync()` inside a per-task `for` loop — that's O(N × totalNotifications) scanning per fetch cycle. With 500 notifications and 100 tasks, that's 50,000 notification objects scanned every 15 minutes.

**Fix for the O(N²):**

```ts
// cancelTaskReminders — fetch once, cancel in batch, not per-task
export async function cancelTaskRemindersBatch(taskIds: string[]): Promise<void> {
    const scheduled = await Notifications.getAllScheduledNotificationsAsync();
    const idSet = new Set(taskIds);
    const toCancel = scheduled.filter((n) =>
        taskIds.some((id) => n.identifier.startsWith(id))
    );
    await Promise.all(
        toCancel.map((n) => Notifications.cancelScheduledNotificationAsync(n.identifier))
    );
    if (Platform.OS === 'android') {
        await Promise.all(taskIds.map((id) => TaskAlarmModule.cancelAlarm(id)));
    }
}
```

Call this once in the background fetch with all task IDs, not per-task.

## Auto-skip question

Yes, but not a blanket auto-skip. The right split on import:

- `status = 'completed'` or `'skipped'` → import as-is, **no alarms, no status change**
- `status = 'scheduled'` and `endTime < now` and not today → import as `'skipped'`, **no alarms** — they're history, not actionable
- `status = 'scheduled'` and `startTime` is today or future → import normally with alarms

The simplest implementation: in `restoreFromJson`, before calling `addTask`, override the status:

```ts
const now = Date.now();
const taskToImport: Task = {
    ...t,
    status:
        t.status === 'scheduled' && new Date(t.endTime).getTime() < now
            ? 'skipped'
            : t.status,
};
await cb.addTask(taskToImport, { skipAlarms: taskToImport.status !== 'scheduled' });
```

This prevents the alarm-fire-on-import bug entirely and keeps the DB clean. Historical completed/skipped tasks stay as-is. Past scheduled tasks become skipped. Only genuinely upcoming tasks get alarms.
